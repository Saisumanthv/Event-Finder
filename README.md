# Event Finder

Find events, hackathons and courses to showcase your skills or learn new ones.

Event Finder collects listings from 15 websites, then lets you ask a tool-using AI assistant, build a learning path, or browse and filter by hand. Results are split into **Free** and **Paid** sections, and every card links to the original page.

- **Frontend:** React 19 + Vite
- **Backend:** FastAPI (Python 3.12+), Google ADK and the Gemini API

## What you can do

| Control | What it does |
|---|---|
| **Ask the assistant** | Type a request such as *"I know Python and want a hackathon for my portfolio in the next two weeks"*. A tool-calling agent searches the listings (and the web if needed), then answers with picked cards, a one-line reason for each, and a collapsible list of the steps it took. |
| **Build my path** | Type a goal such as *"get into machine learning"*. You get an ordered path of courses, hackathons and events, with a sentence on why each step comes next. |
| **Browse and filter manually** | Collapsed by default. Fill in a profile (skills, interests, level, mode, location) and click **Get Event Details**, **Get Hackathon Details** or **New Courses**. With an empty profile you get everything; with a profile you get only what fits, each with a reason. The profile is saved in your browser (`localStorage`). |

Every card shows a summary, a difficulty label, prerequisites, tags, cost, mode, date and its source website. While a request runs, the loading ring shows the elapsed time in seconds.

### Prep Map (hackathons)

Every hackathon card has a **Prep Map** button in its bottom-right corner. It opens a pop-up with the skills worth learning before taking part. Each skill is a dropdown that expands into topics and subtopics, with **Expand all / Collapse all** and a **Download PDF** button. The PDF contains every skill fully expanded, regardless of what is open on screen.

For hackathons that look AI-related, the pop-up has two tabs:

| Tab | Prepares you to... |
|---|---|
| **Fundamentals** | learn the concepts and tools yourself (for an AI hackathon this includes the machine learning side) |
| **Vibe coding** | build with AI coding assistants and ready-made hosted AI models, with no machine learning background: turning an idea into a spec, prompting an assistant, calling a model API, reading and debugging generated code, shipping a demo, and knowing your own code well enough to explain it |

Some AI hackathons really do need model work (for example training a segmentation model). For those, the Vibe tab shows a warning saying what vibe coding can and cannot cover. Each tab is generated when first opened. The footer offers **This tab (PDF)** and **Both tabs (PDF)**; for hackathons without a Vibe tab it is a single **Download PDF**.

Prep maps are prepared in the background as soon as hackathon cards appear on screen (three at a time, in display order), so the pop-up normally opens instantly. Hovering a card's Prep Map button moves that card to the front of the queue, and opening one that is still being prepared waits for it instead of asking twice. Finished maps are saved on the server, so each hackathon is only generated once.

**Flow chart.** The pop-up's **Flow chart** button opens the current tab's skills in a new browser tab as a flow chart: Start, then each skill in order with its topics and subtopics branching below it, then "Ready to take part". The end node links to the hackathon's page. It is built in the browser from the map already on screen (no extra request). The tab's **Save as PDF** button downloads the chart as a one-page PDF drawn with jsPDF (a long page, so no box is split).

**Learning resources.** Under each topic of an expanded skill there is a **Search YouTube** link (instant, free, no key) and a **Top 2 videos** button. The button asks the backend for the top two YouTube videos for that topic, searched by the topic name plus its first subtopics. One search fetches 10 candidates and plain code drops Shorts (under 4 minutes) and hashtag-stuffed titles, keeps only videos whose title or description mention the topic, and ranks by how many topic words they match, then by views (the extra details call costs 1 quota unit and does not count against the 100-search limit); titles, channels and links come straight from YouTube, not from the AI. It is on demand only, never part of loading a map, because YouTube allows about 100 searches a day. Results are cached for 7 days, the app stops at `YOUTUBE_DAILY_LIMIT` searches a day (default 90), and when the limit or the key is missing the button explains it and the search link still works. Needs `YOUTUBE_API_KEY` (a free YouTube Data API v3 key) on the backend; without it only the search link is offered.

The map is generated by the model from the listing's own details (title, description, tags, prerequisites), so it follows the hackathon's theme. If the listing says little, the map is based on the field the title suggests, and the pop-up says so. It never states dates, prizes, rules or tracks, so check the official page for those. If the model is unavailable, the pop-up lists only the skills named in the listing.

### Ask AI (chat with any card)

Every card, whether event, hackathon or course, has a **💬 Ask AI** button that opens a chat about that one listing. It uses retrieval-augmented generation (RAG):

1. **Ingest.** When the chat opens, the backend takes the card's own fields and downloads the card's page (`link`). It keeps the readable text, including the page's description tags and structured data, since many sites build the rest in the browser. Text is split into passages of about 700 characters and each passage is embedded with Gemini (`gemini-embedding-001`, 768 dimensions). This runs while the user reads the suggested questions, so the first answer is quick.
2. **Retrieve.** Each question is embedded and compared with the passages by cosine similarity. The listing's own facts plus the 4 closest passages are used. If embeddings are unavailable, plain keyword matching picks the passages instead.
3. **Answer.** The model sees only those passages and the last few chat turns. It must say so when the answer is not there instead of guessing, and it never writes links. The page text is treated as data, so instructions hidden in a web page cannot control the chat. The reply lists the passages it used.

The knowledge for the 100 most recent cards is kept in memory (not on disk), so it is rebuilt after a restart. The server only fetches public `http(s)` pages: addresses on private or local networks, odd ports and unsafe redirects are refused. If the page cannot be read (for example a site that renders everything in the browser), the chat uses the listing's details only and says so.

## How it works

```
 15 websites ──► adapters (plain Python) ──► merge, de-duplicate, ids
                                                   │
                                      Gemini enriches each card
                          (summary, difficulty, prerequisites, tags)
                                                   │
                                  in-memory cache + backend/cache.json
                                                   │
        ┌──────────────────┬───────────────────────┼──────────────────┐
     /assistant        /learning-path         /recommend         /button-action
   (agent + tools)     (path planner)         (ranker)           (plain listing)
```

1. **Adapters collect the data.** Each website has a small function in `backend/sources_*.py` that returns cards in one schema. This is ordinary Python (`requests` and `BeautifulSoup`); the model is not involved. Sources are fetched in parallel, and one failing source never breaks the rest.
2. **Gemini enriches the cards** in batches of 20 by adding `summary`, `difficulty`, `prerequisites` and `tags`.
3. **A saved copy keeps it fast.** Items are kept in memory and saved to `backend/cache.json`. Requests read that copy and never scrape. It is refreshed a few times a day on a schedule (see *Keeping the data fresh*), and results show how old it is.
4. **Features read from the cache.** Plain code filters, groups and sorts. The model is used only for language tasks.

### What the model does, and what it never does

| Task | Where | Model returns |
|---|---|---|
| Enrich cards | `enrich_items` | summary, difficulty, prerequisites, tags |
| Rank for a profile | `recommend_items` | item ids in order, plus a short reason each |
| Turn a sentence into filters | `parse_search_query` | a filter object (type, mode, level, cost, dates, keywords) |
| Plan a learning path | `plan_learning_path` | ordered item ids, a reason for each, an overview sentence |
| Prep map for a hackathon | `build_prep_map` | skills, each with topics and subtopics, for the Fundamentals or Vibe coding approach |
| Search the web | `search_web` | structured items, from a Google-grounded search |
| Assistant | `build_assistant` | decides which tools to call, then picks item ids and writes the answer |

**The model never writes titles, dates, prices or links.** Every one of those comes from the source data. Code validates everything the model returns: unknown or duplicate ids are dropped, URLs are stripped from its text, and values outside the allowed sets are ignored. For web search, links come only from the pages Google cites, never from the model's text. If the model fails, each feature falls back to plain code (keyword matching or simple ordering) and the response is flagged `"fallback": true`, instead of returning an error.

### The assistant's tools

The assistant (`backend/agent.py` and the tools in `backend/main.py`) is a Google ADK `LlmAgent` that chooses its own tool calls in a loop:

| Tool | Purpose |
|---|---|
| `search_listings` | Filter the listings by type, mode, level, cost, dates and keywords |
| `get_details` | Look at one item's description, prerequisites and tags |
| `build_learning_path` | Call the path planner for a plan or roadmap |
| `search_the_web` | Google-grounded search, used when the listings do not cover the request |

It can pick only item ids that its tools returned. It gets at most 6 tool calls and 10 model calls per request, enforced in code.

## Data sources

15 websites are live. Each is checked against its `robots.txt` and uses a public API or page data; none needs a key.

| Category | Websites |
|---|---|
| Events | GeeksforGeeks, Confs.tech, Meetup, Luma, HasGeek |
| Hackathons | Unstop, Devpost, MLH, Devfolio, HackerEarth, lablab.ai |
| Courses | GeeksforGeeks, Coursera, Microsoft Learn, edX, Class Central |

These were evaluated and **not** added, and nothing tries to get around their blocks:

| Site | Why |
|---|---|
| Eventbrite | `robots.txt` disallows all automated access |
| GDG, Commudle, Townscript, Hack2skill, DoraHacks, freeCodeCamp, NPTEL | JavaScript-only pages with no usable data or public API |
| Kaggle (competitions and Learn) | Blocks bots behind a CAPTCHA |
| Udemy | Blocked by Cloudflare |
| Google Cloud Skills Boost | `robots.txt` unreadable and a JavaScript-only catalog |

### Cost and the Free / Paid sections

`cost` is `free` or `paid` only when the source states it (for example Unstop's `isPaid` flag, or a price on a course card). Items with no stated price go into a third **Price not listed** group, so they are never wrongly shown as free or paid. Meetup events with no fee information are treated as free, which is an inference.

## Setup

**Requirements:** Python 3.12+, [uv](https://docs.astral.sh/uv/), Node.js and a Gemini API key from [Google AI Studio](https://aistudio.google.com/apikey).

### Backend

```bash
cd backend
uv sync
copy .env.example .env     # Windows
# cp .env.example .env     # macOS/Linux
```

Open `.env` and set:

```
GOOGLE_API_KEY=your-key-here
```

Then start the server:

```bash
uv run uvicorn main:app --reload --port 8000
```

The first start scrapes and enriches all sources, which takes about a minute. The result is saved to `backend/cache.json`, so later starts are fast. Delete that file to force a full refresh.

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Open http://localhost:5173. Locally the frontend calls the backend at `http://127.0.0.1:8000`, and the backend accepts requests from `http://localhost:5173`. Both can be changed for deployment (see below).

## Keeping the data fresh

Opening the website never scrapes anything. The saved copy is refreshed in these cases:

| When | What happens |
|---|---|
| **On a schedule** (default 06:00, 12:00 and 18:00 India time) | Events and hackathons refresh at every time; courses refresh only at the first time of the day, since they change slowly. |
| **From outside**, with `POST /refresh` | Refreshes all categories. Used by an external scheduler such as cron-job.org, which also wakes a sleeping host. |
| **At startup, or on a request, if the copy is older than 6 hours** | The old copy is served at once and a refresh runs in the background. |
| **A request when the copy is older than 12 hours** | The request waits for a fresh copy. If that fails, the old copy is served. |

Refreshes are cheap: a refresh only asks Gemini to write summaries for new or changed items and reuses the earlier summaries for the rest. In a test against the live sites, a refresh of all three categories took 4 to 16 seconds. Single-session events (Meetup, Luma, HasGeek) whose date has passed are hidden even before the next refresh. Every results view shows "Listings updated … ago".

| Setting (environment variable) | Meaning | Default |
|---|---|---|
| `REFRESH_TIMES` | Times of day for the scheduled refresh, `HH:MM`, comma-separated. Empty turns the schedule off. | `06:00,12:00,18:00` |
| `REFRESH_TIMEZONE` | Time zone for those times (an IANA name). | `Asia/Kolkata` |
| `REFRESH_TOKEN` | Secret for `POST /refresh`. Without it the endpoint is off (404). | not set |
| `YOUTUBE_API_KEY` | YouTube Data API v3 key for "Find top videos". Without it only the YouTube search link is shown. | not set |
| `YOUTUBE_DAILY_LIMIT` | Most video searches per day (YouTube's limit is about 100). | `90` |

### Refreshing from cron-job.org

A schedule inside the app only runs while the app is awake, and a free Render instance sleeps when idle. To refresh at set times regardless:

1. In the backend's Environment settings, add `REFRESH_TOKEN` with a long random value.
2. On [cron-job.org](https://cron-job.org) create a job: URL `https://your-backend.onrender.com/refresh`, method **POST**, and under Advanced add the header `X-Refresh-Token` with the same value.
3. Schedule it at the times you want (for example 06:00, 12:00 and 18:00).

The call answers immediately with `202` while the refresh runs in the background. A sleeping free instance takes close to a minute to wake, and cron-job.org gives up on a request after about 30 seconds, so a refresh call that arrives at a sleeping instance may time out without having started. To avoid that, create a second job that calls `GET /health` a few minutes before each refresh (or every 10 minutes to keep the instance awake all day). `/health` is cheap and never scrapes. Check the first scheduled run in the Render logs to confirm it worked.

## Deployment (Render)

Deploy the backend first, because the frontend needs its address.

**1. Backend: Web Service.** Root Directory `backend/`.

| Setting | Value |
|---|---|
| Build Command | `pip install uv && uv sync --frozen` |
| Start Command | `uv run uvicorn main:app --host 0.0.0.0 --port $PORT` |
| `GOOGLE_API_KEY` | your Gemini key |
| `PYTHON_VERSION` | `3.12.8` |

**2. Frontend: Static Site.** Root Directory `frontend`.

| Setting | Value |
|---|---|
| Build Command | `npm install && npm run build` |
| Publish Directory | `dist` |
| `VITE_API_URL` | the backend's URL, such as `https://your-backend.onrender.com` |

`VITE_API_URL` is baked into the build, so after changing it you must redeploy the frontend.

**3. Back on the backend,** add the environment variable `ALLOWED_ORIGINS` set to the frontend's URL, such as `https://your-frontend.onrender.com`. Without it the browser blocks every request (CORS). Use several comma-separated addresses if you have more than one.

The disk on Render is temporary, so `cache.json` is lost on each deploy or restart and the next start takes about a minute and makes about 10 to 15 Gemini calls. Free instances also sleep when idle.

## API

All of these are `POST` with a JSON body. Two more are described under *Keeping the data fresh*: `POST /refresh` (needs the `X-Refresh-Token` header) and `GET /health`. Items share one schema: `id`, `title`, `subtitle`, `category`, `description`, `date`, `location`, `mode`, `tags`, `cost`, `link`, `source`, `summary`, `difficulty`, `prerequisites`.

| Endpoint | Request | Response |
|---|---|---|
| `/assistant` | `{ "message": "..." }` (up to 500 characters) | `{ "answer", "steps": [{ "tool", "detail", "result" }], "cards": [...with "reason"], "fallback" }` |
| `/learning-path` | `{ "goal": "...", "max_steps": 4 }` (2 to 6) | `{ "overview", "path": [...with "step", "type", "why_next"], "fallback" }` |
| `/recommend` | `{ "profile": { "skills", "level", "interests", "mode_preference", "location" }, "limit": 5, "action": "event_details" }` (`action` optional, `limit` 1 to 100) | `{ "recommendations": [...with "rank", "reason"], "fallback" }` |
| `/button-action` | `{ "action": "event_details" }` (or `hackathon_details`, `new_courses`) | `{ "status": "success", "action", "items": [...] }`, or `{ "status": "error", "message", "items": [] }` |
| `/search` | `{ "query": "free weekend hackathons, online" }` | `{ "filters": {...}, "results": [...], "fallback" }` |
| `/web-search` | `{ "query": "..." }` | `{ "results": [...] }`, or an empty list with a `message` |
| `/card-chat/ingest` | `card` (the card's fields, as shown on the page) | `{ "ready", "passages", "page" }`: reads and indexes the card's page |
| `/card-chat` | `card`, `question`, optional `history` (`[{ "role", "text" }]`) | `{ "answer", "sources": [{ "origin", "text" }], "passages", "page", "fallback" }` |
| `/prep-map` | the hackathon's `title` (required) plus optional `subtitle`, `category`, `description`, `summary`, `difficulty`, `tags`, `prerequisites`, and `approach` (`fundamentals`, the default, or `vibe`) | `{ "overview", "basis", "fit_note", "skills": [{ "name", "why", "topics": [{ "name", "subtopics": [...] }] }], "fallback" }` (`fit_note` is only set when the vibe approach fits the hackathon poorly) |

An unknown `action` or an empty text field returns HTTP 400. `/search` and `/web-search` are not used by the current page (the assistant covers both) but still work.

Example:

```bash
curl -X POST http://127.0.0.1:8000/assistant \
  -H "Content-Type: application/json" \
  -d '{"message":"free online courses to learn MERN stack"}'
```

## Adding a source

1. Write a function in the right `sources_*.py` that returns a list of dicts with the keys `title`, `subtitle`, `category`, `description`, `date` (`YYYY-MM-DD` or empty), `location`, `mode` (`online`, `offline`, `hybrid` or empty), `tags`, `cost` (`free`, `paid` or empty) and `link` (the specific item page).
2. Add it to that file's `SOURCES` dictionary. Nothing else changes: enrichment, caching, filtering and the assistant pick it up automatically.

## Limitations and notes

- **Slow first load.** A cold start takes about a minute. Assistant requests take roughly 15 seconds when the listings are enough, and about a minute when they use web search.
- **Model cost.** Enrichment, the assistant and web search all call Gemini. Filling an empty cache makes roughly 10 to 15 calls; later refreshes only ask about new or changed items, so they cost little. One assistant request typically makes several calls.
- **Generated fields are estimates.** `difficulty`, `summary`, `prerequisites` and `tags` come from the model and can be wrong. For example, a course the site calls "Beginner to Advanced" may be labelled "intermediate".
- **Web search is less reliable.** Results come from Google's cited pages, so dates and prices can be missing or off, and links are checked only loosely against the title. The page marks them as coming from the web.
- **Fragile adapters.** Meetup, Luma, HasGeek, Devfolio, Class Central, edX and MLH read page structure or undocumented endpoints, so a site redesign can break them. A broken adapter is skipped and logged; the rest keep working.
- **Source quirks.** Luma shows Bengaluru only, and Meetup's results follow the server's location. Devpost's `date` is the start date, which has already passed for events that are currently open. For Unstop, `date` is the registration deadline. HackerEarth and lablab.ai currently list only a couple of events.
- **Terms of service.** The adapters follow each site's `robots.txt`, but sites such as Coursera, edX, Class Central and Meetup may restrict scraping in their terms. lablab.ai's `robots.txt` asks that its content not be used for AI training. Check them before using this beyond personal use.
- **Prep Maps are AI suggestions.** They are generated from the listing text, can be generic when that text is thin, and are saved in `backend/prep_cache.json` (up to 400 maps, each approach separately). The Vibe tab is shown when the listing mentions AI-related words, which is a keyword check, so it can appear for hackathons where vibe coding is a poor fit; the map then carries a warning. The PDF uses the standard PDF fonts, so characters outside Latin-1 (emoji, non-Latin scripts) are left out.
- **Prep Map cost.** Preparing in the background means a model call for every hackathon you display, plus a second one for AI-looking ones (the Vibe tab). Showing all 60 or so hackathons for the first time makes about 80 calls and takes several minutes to finish; after that they are free. On Render the disk is temporary, so the saved maps are lost on each deploy or restart.
- **Card chat limits.** Answers are only as good as the text found. Sites that load their content with JavaScript (Unstop and Devfolio pages, for example) often give only a short description, so the chat may answer that something is not in the listing. The chat makes one embedding call per passage when it opens and one model call per question, so every open chat costs model usage; the endpoints have no rate limit of their own.
- **No automated tests are included in the repository.**
